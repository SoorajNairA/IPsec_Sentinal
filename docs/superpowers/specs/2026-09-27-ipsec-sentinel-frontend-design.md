# IPsec Sentinel Frontend Design Specification

**Status:** Proposed for review

**Date:** 2026-09-27

**Base commit:** `64b5884edc9cac3ceea321ce785f36cb24132401`

**Target branch:** `feat/ipsec-sentinel-frontend`

## 1. Purpose

This milestone turns the validated IPsec Sentinel analyzer into a polished local security-forensics instrument. The interface must let a judge understand the product's central idea within 30 seconds: IPsec payloads remain encrypted, while defensible protocol evidence and encrypted-traffic behavior can still reveal tunnel configuration, security posture, and likely workload class.

The frontend consumes the existing `ipsec-sentinel.analysis/v1` contract, preserves evidence provenance, and supports both instant guided demonstrations and live local PCAP analysis. It does not expand analyzer research, retrain the model, modify the dataset, or introduce a general-purpose backend.

## 2. Product and Trust Principles

The product must feel like a serious SOC/research instrument rather than a generic dashboard. Its hierarchy is:

1. the reconstructed IPsec tunnel;
2. the security posture and evidence coverage;
3. the distinction between observed, derived, AI-inferred, and unknown claims;
4. encrypted traffic behavior without payload decryption; and
5. actionable findings and limitations.

The interface must never imply that ESP payloads were decrypted. Wherever traffic intelligence is shown, the UI states that it is derived from encrypted packet size, direction, and timing, and that confidence is raw and uncalibrated.

All technical values originate from the analyzer contract, a clearly named deterministic presentation derivation, or a static explanation mapping. The frontend must not invent findings, cryptographic values, packet references, confidence values, or evidence.

## 3. Selected Architecture

The selected approach is a local hybrid application with two complementary paths:

- **Guided demo path:** checked-in analysis fixtures generated by the real analyzer from genuine project PCAPs provide instant, deterministic demonstrations.
- **Live analysis path:** a minimal localhost Python bridge accepts a PCAP, invokes the existing `analyze_capture()` pipeline directly, and returns the analyzer result.

The application is a React and TypeScript single-page interface built with Vite. It uses a small set of accessible headless primitives, one icon family, native SVG/CSS visualizations, and a focused motion library. It does not use a chart dashboard template or a large visualization engine.

The Python bridge is an integration adapter, not a new service architecture. It has no database, authentication, telemetry, remote access, or analyzer duplication. It serves only local static assets and the narrow analysis operation required by the prototype.

## 4. Contract Boundary and Data Flow

### 4.1 Analysis contract

The frontend accepts only schema ID `ipsec-sentinel.analysis/v1` and analysis version `1.0`. A runtime contract validator checks required top-level structures, provenance values, evidence identifiers, finding evidence links, score bounds, and assessed/unassessed weight consistency before a result enters application state.

The raw analyzer object remains immutable. Formatting and frontend view models are pure derivations. Unknown or absent values remain unknown; they are never replaced with plausible-looking defaults.

### 4.2 Live-analysis envelope

The bridge returns an integration envelope with two explicitly separate namespaces:

```text
analysis: exact ipsec-sentinel.analysis/v1 result
xray: deterministic presentation projection from the same capture
```

`analysis` is not extended with frontend-only fields. The `xray` projection contains only ESP metadata already produced by the current parsing path: relative timestamp, captured length, normalized direction, and an optional bounded sampling marker. It contains no payload bytes, plaintext headers from inside ESP, labels, scenario names, or fabricated packets.

For large captures, a deterministic display sampler may reduce rendered points while preserving first/last points, direction changes, size extremes, and temporal buckets. Aggregate totals continue to come from `analysis.esp`, not from the sampled display data.

### 4.3 Guided-demo artifacts

The demo set contains:

- Secure Baseline;
- AES-128-GCM;
- AES-256-CBC;
- PFS Disabled; and
- Video Traffic Intelligence.

Every bundled analysis JSON is generated by the analyzer at the base or descendant implementation commit from a genuine existing capture. Each has a separate manifest recording the source run/capture, analyzer commit, generation command, schema ID, and SHA-256 digest. X-Ray sidecars are deterministically generated from the same captures. Hand-authored successful analysis objects are forbidden.

The primary judging story uses PFS Disabled, then moves into X-Ray and evidence inspection. The Video demonstration exists to provide a strong real ML-classification example.

## 5. Application State Model

The top-level experience has explicit states:

- `EMPTY`: polished landing and capture chooser;
- `DEMO_CHOOSER`: deterministic guided-demo selection;
- `ANALYZING`: real local orchestration stages;
- `READY`: validated analysis workspace;
- `ERROR`: categorized, user-facing failure; and
- `UNSUPPORTED`: valid request whose capture format/layout is unsupported.

Analysis stages are shown only while a genuine bridge request is running. They communicate orchestration progress but do not reveal or fabricate technical results before the completed analyzer response is validated.

The bridge normalizes expected failures into stable error codes while retaining safe detail for diagnostics. Python tracebacks are logged locally for development but never rendered to the user.

## 6. Information Architecture

The compact primary navigation contains:

- Overview;
- Tunnel;
- Traffic;
- Security;
- Evidence; and
- Report.

Navigation is client-side and preserves the loaded analysis, selected evidence, language mode, and X-Ray state. Deep route proliferation is avoided. The evidence inspector is a global side drawer so the same provenance interaction works from every view.

Desktop is the primary canvas. At tablet widths, supporting columns reposition beneath the signature visualization. Mobile retains all analysis functions but uses a compact top bar, horizontally scrollable route control where necessary, and a full-width evidence sheet.

## 7. Visual System

The system uses a near-black graphite canvas, subtly differentiated graphite surfaces, warm off-white primary text, cool-gray secondary text, restrained icy blue for protocol and AI state, green only for verified positive state, amber for caution, and red only for real high-risk findings.

Surfaces rely on fine borders, tonal depth, disciplined spacing, and sparse grid lines. They avoid glassmorphism, large glows, decorative terminal text, random hexagons, and repeated equal-weight cards.

A professional sans-serif handles normal interface text. A monospace face is limited to SPIs, evidence IDs, packets, timestamps, protocol identifiers, and normalized cryptographic values. Typography, spacing, border, radius, motion, and status colors are centralized as design tokens.

Icons come from one consistent family. Status distinctions always combine shape, label, and text treatment rather than color alone.

## 8. Landing and Analysis Transition

The empty state presents:

- `IPsec Sentinel`;
- “See what your encrypted tunnel actually reveals.”;
- primary `Analyze Capture` action;
- secondary `Run Guided Demo` action; and
- `Local Analysis`, `Payload Decryption: Never`, and `Evidence-Aware Results` trust indicators.

The capture target supports file selection and drag/drop for `.pcap` and known unsupported `.pcapng` detection. It is a compact instrument intake area, not a marketing hero.

When analysis starts, the intake area transforms into a restrained stage sequence: reading capture, detecting IPsec, parsing IKE, reconstructing SAs, analyzing ESP behavior, running traffic intelligence, and evaluating security posture. The completed workspace enters through a short transition that prioritizes the tunnel visualization.

## 9. Overview and Live Tunnel

The Overview is the strongest result screen. Its main area is a data-driven SVG tunnel connecting the analyzer's initiator and responder. It displays IKE version, responder-selected encryption, DH group, current ESP activity, SA/SPIs, and PFS state where evidence permits.

The tunnel visualization uses:

- endpoint nodes labeled from `analysis.peers`;
- a layered tunnel path whose state reflects IPsec detection;
- restrained moving ESP markers scaled from real packet rate and directional balance;
- a handshake anchor for IKE evidence;
- rekey markers derived from SA chronology;
- contextual warnings attached to the relevant tunnel property; and
- a key-exchange layer that visibly identifies disabled or unknown PFS.

Animation communicates establishment and packet flow, not decoration. Reduced-motion mode shows the same state with static direction markers and instantaneous transitions.

A supporting security rail shows score, evidence coverage, IKE version, cipher, DH, PFS, traffic prediction, raw confidence, and highest-priority findings using varied visual grouping rather than six identical cards.

## 10. X-Ray Encrypted Traffic

X-Ray is a deliberate alternate representation of the same tunnel session. It renders a temporal SVG ribbon from the real `xray` projection:

- horizontal position represents relative time;
- vertical side represents direction;
- mark length/thickness represents captured packet size;
- inter-mark distance exposes inter-arrival gaps;
- grouped marks expose bursts; and
- a density track summarizes long sessions.

Aggregate annotations come from `analysis.esp.features`, including size distributions, direction ratios, packet/byte rates, idle gaps, burst counts, and duration. The rendering must never synthesize a plausible packet sequence from aggregates when per-packet projection is unavailable; it falls back to an honest aggregate-only view.

The view prominently states `Payload visibility: 0%` and `Behavioral metadata available`. AI output includes provenance, predicted class, model/version, probability distribution, and `Raw / uncalibrated` confidence. A short explanation makes clear that payload contents remain encrypted.

## 11. Evidence Provenance and Inspector

Four provenance states have distinct accessible markers:

- **OBSERVED:** solid marker for direct packet evidence;
- **DERIVED:** linked-node marker for deterministic conclusions;
- **AI-INFERRED:** analytical waveform marker for model output; and
- **UNKNOWN:** outlined marker for insufficient evidence.

Every important value with evidence exposes a visible provenance affordance and an accessible “How do you know?” action. Hover may preview provenance, but critical content never requires hover.

Selecting a value opens the evidence drawer with:

- displayed value and provenance;
- evidence ID;
- evidence description;
- packet numbers and timestamps;
- protocol;
- raw and normalized values;
- source component;
- confidence where present; and
- a concise, provenance-aware explanation.

Finding links resolve through the contract's `evidence_ids`. When several records support a claim, the drawer provides a compact evidence sequence. Missing or invalid links are displayed as unavailable and treated as a contract-validation defect in tests, never silently substituted.

## 12. Detailed Views

### 12.1 Tunnel

The Tunnel view expands the endpoint and protocol relationship into an SA timeline. It shows IKE, CHILD SAs, directional SPIs, successor relationships, rekey chronology, and PFS evidence attached to the relevant transition. A compact technical table supports the visual but does not replace it.

### 12.2 Traffic

The Traffic view centers X-Ray, followed by predicted class, raw confidence, probability distribution, model/version, feature-schema version, packet count, bytes, duration, packets per second, and directional balance. Unknown, insufficient-packet, missing-model, and low-confidence states receive purposeful layouts rather than empty charts.

### 12.3 Security

Security renders only analyzer findings. Findings are grouped into Cryptography, Key Exchange / PFS, SA Hygiene, Protocol / Replay, and Metadata / Privacy. High and medium issues lead; passing/informational observations are visually quieter.

Each expandable finding shows summary, why it matters, recommendation, status, provenance, and evidence actions using existing contract values. Static frontend wording may clarify a rule without changing its meaning or severity.

### 12.4 Evidence

The Evidence view is a dense chronology/list with All, Observed, Derived, AI-Inferred, and Unknown filters plus accessible search. Selection opens the shared inspector. Packet references, timestamps, source component, and protocol use technical formatting.

### 12.5 Report

The Report is an on-screen, print-aware composition with Executive Summary, Security Score, Protocol Configuration, Traffic Intelligence, Key Findings, Risk Summary, Evidence Coverage, Recommendations, and Limitations. It uses the same contract-derived view models as the workspace and does not create new conclusions. Print styles remove navigation and controls while retaining provenance labels and honest limitations.

## 13. Transparent Security Score

The score uses a precise segmented composition, not a speedometer. It presents total score, maximum, assessed evidence coverage, unassessed percentage, and the analyzer's scoring method together.

Category rows show achieved versus maximum score and assessed/unassessed weight. Deductions are clickable and resolve to their finding and evidence. Unknown weight is visibly unassessed, not presented as a penalty. The UI must not convert a high score with low evidence coverage into a confident “secure” verdict.

## 14. Technical and Plain-English Modes

A secondary global toggle changes explanatory copy, not raw values or findings. Technical mode retains protocol terminology. Plain-English mode uses reviewed static mappings for known analyzer concepts, such as explaining a CHILD-SA rekey without fresh DH material.

Mappings are versioned with the frontend, tested for semantic equivalence, and fall back to analyzer text when no accurate mapping exists. No live LLM is involved.

## 15. Error and Unknown States

The UI includes distinct states for:

- capture contains no detected IPsec;
- malformed PCAP;
- unsupported PCAPNG;
- unsupported link/capture layout;
- insufficient ESP packets;
- model unavailable;
- analyzer failure;
- low-confidence traffic inference; and
- field-level unknown evidence.

Each state explains what is known, what could not be assessed, and a practical next action where one exists. Analyzer messages are mapped conservatively; unexpected errors use a generic safe message and a local diagnostic reference.

Upload handling enforces a configurable local size limit, writes to a unique temporary directory, sanitizes the submitted filename, never shells through user-controlled text, and removes temporary artifacts after response or failure.

## 16. Motion, Accessibility, and Responsiveness

Motion is limited to tunnel materialization, packet flow, X-Ray transition, evidence drawer, score transition, finding expansion, and short view transitions. It must not delay interaction or run continuously without informational value.

`prefers-reduced-motion` disables path drawing, packet travel, morphing, and animated number changes while preserving state and direction. Controls are semantic, fully labeled, keyboard reachable, visibly focused, and usable without tooltips. Drawers trap focus appropriately and restore focus on close. Contrast targets WCAG AA for interface text and controls.

The required visual QA viewports are:

- 1440×900;
- 1280×800;
- 768×1024; and
- 390×844.

Desktop layouts preserve information density. Tablet and mobile change composition deliberately rather than blindly stacking every surface.

## 17. Testing Strategy

### 17.1 Unit and component tests

Tests cover:

- v1 contract loading and rejection;
- unknown values and absent optional detail;
- provenance markers and evidence resolution;
- security score and evidence-coverage rendering;
- findings grouping and expansion;
- ML raw-confidence and low-confidence rendering;
- genuine demo artifact validity and digests;
- deterministic presentation derivations;
- route/view navigation and retained state;
- technical/plain-English mappings; and
- categorized error states.

Frontend behavior is developed test-first. Pure adapters and view-model derivations receive focused unit tests; interactive components receive semantic component tests.

### 17.2 Bridge tests

Bridge tests cover valid PCAP analysis, strict v1 response validation, X-Ray projection fidelity, malformed/unsupported inputs, upload limits, temporary-file cleanup, safe error normalization, and analyzer/model unavailability. Critical analyzer logic is invoked rather than mocked in integration tests.

### 17.3 Playwright paths

Local Playwright, used because no Playwright MCP is available, verifies:

- Secure Demo: load, Overview, Tunnel, Evidence, Report;
- No-PFS Demo: warning, score deduction, finding, evidence interaction;
- Video Demo: AI-inferred classification, raw confidence, X-Ray;
- live or fixture-backed unsupported capture error;
- keyboard navigation and evidence-drawer focus;
- reduced-motion behavior;
- browser console and failed requests; and
- the four required viewport sizes.

## 18. Mandatory Visual QA Loop

Implementation does not proceed as one unreviewed styling pass.

### Review 1: shell, Overview, tunnel

Rendered screenshots are inspected for hierarchy, spacing, typography, density, generic-template appearance, alignment, and tunnel prominence. Defects are corrected before Traffic or Security becomes the focus.

### Review 2: Traffic/X-Ray, Security

Real demo data is inspected for chart clutter, unreadable labels, excessive card treatment, incorrect status hierarchy, visual noise, truthful packet rendering, and confidence language. Defects are corrected before final views.

### Review 3: Evidence, Report, responsive states

All required viewports are inspected for overflow, typography, interaction targets, drawer behavior, and print/report composition. Mobile remains functional without reducing the desktop interface to a generic stacked dashboard.

### Final review

Playwright runs the guided story end to end. The review checks console errors, failed requests, keyboard navigation, focus restoration, reduced motion, responsive layouts, and final screenshots. Completion is blocked until the rendered product passes the following questions:

1. Does this look like an AI-generated dashboard?
2. Would a cybersecurity engineer believe this belongs to a serious analysis product?
3. Can a judge understand the core innovation within 30 seconds without narration?

Any unfavorable answer requires another refinement pass.

## 19. Performance and Operational Constraints

The frontend avoids WebGL, 3D engines, background video, and oversized chart packages. SVG point counts are bounded through deterministic display sampling. Noncritical views may be code-split, while Overview and shared evidence infrastructure remain immediate.

The live bridge binds to loopback only. Guided demos require no analyzer process and remain reliable if the live bridge or model is unavailable. The interface clearly distinguishes a guided artifact from a newly analyzed upload.

## 20. Tooling Decisions

Environment discovery found no shadcn, Playwright, or current-documentation MCP. Therefore:

- accessible primitives will be installed and verified through their official packages/documentation rather than invented APIs;
- local Playwright will provide browser automation, screenshots, console checks, and viewport validation;
- current official documentation will be consulted when implementation depends on unstable library APIs; and
- native SVG/CSS will implement the signature tunnel, SA timeline, provenance marks, and X-Ray rather than generated raster assets.

The implementation will use the relevant Superpowers workflows for planning, test-driven development, systematic debugging, execution, code review, and completion verification.

## 21. Regression and Non-Goals

The milestone must preserve the analyzer, dataset, ML, and prior privileged integration behavior. It must not modify the 168-session dataset, retrain/export the model, add new traffic/IPsec scenarios, or rewrite backend history.

It does not build cloud VPN infrastructure, authentication, user accounts, telemetry, analytics, a database, Electron packaging, an OOD classifier, NAT-T deep analysis, IPv6 analysis, or PCAPNG parsing.
